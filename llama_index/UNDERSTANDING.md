# LlamaCloud proof-of-concept checklist

## Problem

- [ ] Explain why ten table-bearing pages are more useful than the first ten PDF pages.
- [ ] Explain why isolated table pages can still break tables whose headers or rows continue on adjacent pages.
- [ ] Explain why printed page numbers and PDF viewer page numbers differ by one here.
- [ ] Explain why the same ten-page sample must be used for every comparison.

## Solution

- [ ] Explain why the official Python SDK is used instead of adding a second Node.js environment.
- [ ] Explain that Parse reconstructs document content as Markdown or a spreadsheet.
- [ ] Explain that Extract maps content into a schema-controlled JSON structure.
- [ ] Explain why Parse and Extract need separate settings even when they share one fidelity prompt.
- [ ] Explain why the active rerun targets pages in the original PDF instead of concatenating a sample PDF.
- [ ] Explain that Index supports retrieval and questions rather than table reconstruction.
- [ ] Explain why raw responses are retained beside convenient outputs.

## Edge cases and impact

- [ ] Check multi-page tables, blank cells, conflicting headings, and printed units.
- [ ] Check that every Parse table has a corresponding Extract table before accepting completeness.
- [ ] Explain why Parse item page numbers are authoritative but page fields generated by Extract are only model claims.
- [ ] Explain why detecting both halves of a continued table is not the same as stitching them into one table.
- [ ] Distinguish blank, dash, explicit zero, ordinary value, and illegible cell states.
- [ ] Treat generated XLSX and JSON as extraction results, not audited financial data.
- [ ] Compare completeness, cell fidelity, provenance, cost, and elapsed time.
